# Plano de atualização v4.0 — delphi-dev para Claude Code, Codex e OpenCode + hooks religados

> Criado em 2026-10-13, reorganizado em sprints em 2026-10-14. Branch: `feature/v4.0-multi-agente`.
> Plano de **release** (sprints e decisões), não plano de tarefas TDD. Itens marcados com 🧠
> passam por `superpowers:brainstorming` → spec → `writing-plans` antes de código.

## 1. Objetivo

1. Qualquer dev que use **Codex** ou **OpenCode** instala o `delphi-dev` e recebe as mesmas
   skills, comandos, agentes, KB e hooks que o usuário do Claude Code — com degradação explícita
   onde o agente não tiver o recurso.
2. **Religar os hooks** na próxima versão, sem repetir o desastre da v2.2.2.
3. **Estruturar de vez o ciclo de vida do `rag.db`**: o mantenedor publica a própria base quando
   quiser, e usuários do plugin contribuem de volta.
4. **Um repositório só.** Tudo vive aqui. Onde um agente exigir artefato próprio (skill, agent,
   hook), ele é criado aqui, de preferência gerado a partir da fonte única.

Riscos externos: reescrita **V2** do OpenCode muda a API de plugin; subagentes do Codex "podem mudar".

## 5. Princípios de desenho

1. **Skill é a unidade portátil.** Command e agent são cascas finas que apontam para a skill.
2. **Texto neutro de ferramenta.** Nada de "Agent tool"/"Edit tool"/"via Task".
3. **Nada roda dependendo de build na máquina do usuário.** O que roda em hook/MCP é commitado,
   compilado, sem dependência nativa.
4. **Artefatos por agente são gerados** (`scripts/src/build-targets.ts`); a CI falha se estiverem
   desatualizados.
5. **A KB é servida por MCP** (comum aos três). O hook de injeção é casca fina da mesma biblioteca.

## Sprint 4 — OpenCode "enxerga" o plugin

Ideia do usuário: assim como o Claude lê `CLAUDE.md` e o OpenCode lê `AGENTS.md`, o OpenCode só
precisa **ver** o que o plugin já tem. Sem cópias, sem reescrever.

Ressalva técnica: o OpenCode não procura no cache de plugins do Claude, então alguém precisa
apontar para lá — e o caminho do cache muda a cada versão. Proposta:

- [ ] **4.1** Um checkout estável (`~/.delphi-dev/`, atualizado pelo `npx delphi-dev update`).
- [ ] **4.2** O installer **aponta** o OpenCode para ele no `~/.config/opencode/opencode.json`:
      `skills.paths`, `instructions` (um `AGENTS.md` do plugin) e `mcp`. Commands e agents por
      junction (`commands/delphi-dev` → pasta gerada), já que o glob do OpenCode é recursivo.
- [ ] **4.3** Gerador produz `opencode/commands/*.md` e `opencode/agents/*.md` (frontmatter
      `mode: subagent`, `permission`), a partir dos mesmos `commands/`/`agents/`.
- [ ] **4.4** Plugin JS mínimo só para hooks (`tool.execute.after` → fix-encoding;
      `chat.message` → KB), chamando o mesmo JS via `node` (Bun não carrega módulo nativo — e com
      D2 nem precisa).
- [ ] **4.5** Teste com modelo Claude **e** GPT (no GPT, `edit`/`write` viram `apply_patch`).

## 7. Armadilhas

- Não recolocar hooks apontando para `dist/` não versionado nem para módulo nativo.
- Não deixar o installer editar `settings.json` de forma destrutiva — hooks são do plugin.
- Não manter cópias manuais por agente: o que é de Codex/OpenCode sai do gerador.
- Não simplificar o `source` aninhado do `marketplace.json` — o Codex o aceita como está.
- FTS5 é lexical: pergunta em inglês contra KB em pt-BR acha menos. Medir no 1.3 antes de decidir
  se a KB precisa de sinônimos/tags bilíngues.
- Branch longa: o hotfix 3.2.1 vai para `master` por cherry-pick, não por merge da branch.
