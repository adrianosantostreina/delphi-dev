# Design — Base de conhecimento v4: FTS5 local, MCP, hooks religados e ciclo mantenedor ⇄ comunidade

> Spec de 2026-10-14. Branch `feature/v4.0-multi-agente`. Cobre o **Sprint 1 (itens 1.3–1.7)** e o
> **Sprint 2** de [`../plans/2026-10-13-v4.0-multi-agente.md`](../plans/2026-10-13-v4.0-multi-agente.md),
> mais os comandos `/update` e `/about`. Itens 1.1 (`fix-encoding` sem BOM em `.dfm`/`.fmx`) e
> 1.2 (`removeHooks` preservando hooks de terceiros) já estão feitos (`5982e36`, `d74fd3d`).

## 1. Objetivo

1. Qualquer instalação (marketplace do Claude Code, Codex, OpenCode, `npx`) tem a base de
   conhecimento disponível **desde o primeiro minuto**, sem baixar banco e sem dependência nativa.
2. Hooks religados sem repetir a v2.2.2: nada que roda na máquina do usuário depende de build
   local, módulo nativo ou rede no caminho crítico.
3. O mantenedor publica conhecimento quando quiser, **sem lançar versão do plugin**, e todo
   usuário recebe em até 24 h (ou na hora, com `/update`).
4. Usuários contribuem aprendizados de volta com privacidade verificável, e tudo passa pela
   revisão do mantenedor.

## 2. Decisões travadas no brainstorm

| # | Decisão |
|---|---|

| Q2 | Comando **`/update`**: atualiza a base na hora; para o plugin, mostra/roda o comando nativo do agente e avisa que é preciso reiniciar a sessão. |

| Q4 | Sugestão ativa com três respostas: **Aprovar / Recusar / Não mostrar novamente** (en-US: Approve / Decline / Don't show again). No `/contribute-kb` manual, só Aprovar / Recusar. |
| Q4b | Idioma: o da conversa; o do sistema operacional só desempata. |

| Q6 | Base chega ao agente por **hook enxuto** (só em prompt de Delphi, ≤ 3 trechos) **+ MCP** para aprofundar. |

## 3. Arquitetura

```
kb/                      ← workspace npm novo (fonte + testes)
  src/
    paths.ts             raiz do plugin, pasta de dados, URLs
    snapshot.ts          lê um conjunto de .md → documentos + hashes
    chunk.ts             documento → seções (H2)
    index.ts             índice FTS5 (kb.db): build, open, troca atômica
    search.ts            consulta, precedência de tier, corte, snippet
    manifest.ts          gera e compara kb-manifest.json
    update.ts            checa kb-latest, baixa .md alterados, troca atômica
    active.ts            decide qual snapshot vale (embutido x atualizado)
    delphi-intent.ts     "este prompt é sobre Delphi?"
    secret-scan.ts       detecta segredos (contribuição e CI)
    prefs.ts             config.json (suggestions, offline) e state.json
    contribute.ts        envio via gh ou URL de issue
    sync.ts              /sync-kb: compara base compartilhada x knowledge/
    hook-inject.ts       fachada UserPromptSubmit
    hook-fix-encoding.ts fachada PostToolUse
    mcp-server.ts        fachada MCP (stdio)
    cli.ts               fachada CLI (manifest, validate, scan, update, contribute, sync, issue-to-file)
  __tests__/
runtime/                 ← bundles esbuild COMMITADOS, um arquivo por fachada (.mjs)
  hook-inject.mjs  hook-fix-encoding.mjs  kb-mcp.mjs  kb-cli.mjs
hooks/hooks.json         ← hooks declarados pelo plugin
.claude-plugin/plugin.json  ← mcpServers: servidor MCP declarado pelo plugin
```

- **`runtime/` é commitado de propósito**: é o que roda no usuário. O nome evita confusão com a
  regra "`dist/` não se versiona". A CI refaz os bundles e falha se `git diff runtime/` não for vazio.
- Cada bundle embute suas dependências (SDK do MCP inclusive). **Nenhum `npm install` no usuário.**
- A raiz do plugin é derivada do próprio arquivo (`runtime/x.mjs` → `..`). Não depende de
  `CLAUDE_PLUGIN_ROOT` em tempo de execução, só na linha de comando do hook/MCP.

### 3.1 Pasta de dados

`DELPHI_DEV_DATA` se definida, senão **`~/.delphi-dev/`** — a mesma em todos os agentes, para
hook, MCP e CLI concordarem sem depender de variáveis específicas de cada agente.

```
~/.delphi-dev/
  kb-cache/current/      snapshot atualizado (mesma árvore de knowledge/) + manifest.json + meta.json
  kb.db                  índice FTS5 (cache; apagar é seguro)
  config.json            { "suggestions": "on" | "off", "offline": false }
  state.json             { "lastCheck": ISO, "lastResult": "...", "remoteCommit": "..." }
  logs/kb.log            erros de hook/MCP/atualização (rotaciona em 1 MB)
```

### 3.2 Variáveis de ambiente

| Variável | Efeito |
|---|---|
| `DELPHI_DEV_DATA` | Troca a pasta de dados (testes, CI). |
| `DELPHI_DEV_KB_OFFLINE=1` | Nunca acessa a rede; usa só o embutido (ou o cache existente). Equivale a `offline: true`. |
| `DELPHI_DEV_KB_SOURCE=embedded` | Ignora o cache e usa só `knowledge/` do plugin. **Para o mantenedor** rodando do checkout. |

## 4. Modelo de dados

### 4.1 Documento e tier

- Arquivos `*.md` sob `knowledge/{core,fmx,community}/`, exceto `INDEX.md`.
- **Tier pela pasta**: `core`/`fmx` → `canonical`; `community` → `community`. Não existe mais `local`.
- **Frontmatter**: opcional em `canonical`, **obrigatório** em `community` (`title`, `category`,
  `tags`, `source`; `lang` opcional). Sem frontmatter: `title` = primeiro H1; `category` = `fmx` para
  `fmx/`, `general` para `core/`; `tags` = vazio.

### 4.2 Seções (unidade indexada)

- Um documento é dividido nos seus **H2** (`## `). O texto antes do primeiro H2 vira a seção
  "introdução". Documento sem H2 = uma seção.
- Seção acima de 4.000 caracteres é cortada em parágrafos até caber.

### 4.3 Índice FTS5 (`kb.db`)

```sql
CREATE VIRTUAL TABLE sections USING fts5(
  title, heading, body, tags,
  path UNINDEXED, tier UNINDEXED, category UNINDEXED,
  tokenize = 'unicode61 remove_diacritics 2'
);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- snapshot_id, built_at, schema
```

- `snapshot_id` = sha256 da lista ordenada `path:sha256` do snapshot ativo. Índice com
  `snapshot_id` diferente do snapshot ativo é refeito.
- Pesos do `bm25()`: title 5, heading 3, body 1, tags 4.
- **Construção**: grava em `kb.db.tmp-<pid>` e troca por rename. Leitor que achar índice ausente ou
  velho constrói o seu; duas construções simultâneas produzem o mesmo conteúdo, a última troca vence.

### 4.4 `kb-manifest.json`

```json
{
  "schema": 1,
  "commit": "<sha do master>",
  "generatedAt": "2026-10-14T15:30:00Z",
  "pluginVersion": "4.0.0",
  "files": [{ "path": "core/dfm-fmx-sem-bom.md", "sha256": "…", "bytes": 1834 }]
}
```

Gerado **só pela CI**, nunca commitado. `pluginVersion` vem de `.claude-plugin/plugin.json` naquele
commit e alimenta o "há versão nova do plugin" do `/update`.

## 5. Snapshot ativo e atualização

### 5.1 Qual snapshot vale (`active.ts`)

1. `DELPHI_DEV_KB_SOURCE=embedded` → embutido.
2. Existe `kb-cache/current/` **e** `meta.json.pluginVersion` == versão do plugin instalado → atualizado.
3. Caso contrário → embutido. (Plugin atualizado invalida o cache, que é rebaixado na próxima checagem.
   Evita um cache velho, de meses offline, passar por cima de um plugin novo.)

Como o `kb-latest` é refeito a cada merge no `master` e releases saem do `master`, ele nunca está atrás
de um plugin publicado: **se o remoto difere do ativo, o remoto vence**.

### 5.2 Ciclo de atualização (`update.ts`)

1. **Quando**: na subida do MCP, se `now - lastCheck > 24 h`, em segundo plano; ou `kb_update(force)`.
   **O hook nunca acessa a rede.**
2. Baixa `https://github.com/adrianosantostreina/delphi-dev/releases/download/kb-latest/kb-manifest.json`
   (timeout 5 s).
3. Compara com os hashes do snapshot ativo. Igual → grava `lastCheck` e termina.
4. Copia o snapshot ativo para `kb-cache/staging-<pid>/`, baixa só os arquivos novos/alterados de
   `https://raw.githubusercontent.com/adrianosantostreina/delphi-dev/<commit>/knowledge/<path>`, apaga
   os que saíram do manifest, **confere o sha256 de cada arquivo baixado**.
5. Qualquer falha (rede, hash, disco) → apaga o staging, mantém o atual, registra em `state.json`.
6. Sucesso → grava `manifest.json` e `meta.json` (`pluginVersion` instalado, `commit`) no staging;
   `current` → `old-<pid>`, `staging` → `current`, apaga `old`. Refaz o índice.
7. Limite total de 60 s.

## 6. Hooks (`hooks/hooks.json`)

```json
{
  "hooks": {
    "PostToolUse": [{ "matcher": "Write|Edit|MultiEdit",
      "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/runtime/hook-fix-encoding.mjs\"" }] }],
    "UserPromptSubmit": [{
      "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/runtime/hook-inject.mjs\"" }] }]
  }
}
```

A forma final da linha de comando depende da validação §6.3.

### 6.1 `hook-fix-encoding`

- Claude Code: caminho em `tool_input.file_path`.
- Codex: `tool_name` = `apply_patch`; os caminhos são extraídos de qualquer string do `tool_input` que
  contenha `*** Begin Patch`, nas linhas `*** Add File: `, `*** Update File: ` e `*** Move to: `.
  Caminhos relativos são resolvidos contra `cwd` do payload.
- BOM só em `.pas`/`.dpr`/`.dpk`/`.inc`. Node ≥ 18.
- **`.dfm`/`.fmx` nunca recebem BOM** (o leitor de forms dá `Invalid stream format`) **e acento cru
  também quebra** (sem BOM o compilador de recursos lê como ANSI → "ServiÃ§o" na tela). O hook
  reescreve no formato que o próprio IDE grava: caractere não-ASCII **dentro de literal de string**
  vira escape `#NNN` por unidade UTF-16 (`'Serviço'` → `'Servi'#231'o'`; `''` continua sendo a aspa
  escapada). Se o arquivo ficar ASCII puro, um BOM existente é removido. Se sobrar não-ASCII fora de
  string (identificador como `object mnItOpções`), o BOM original é **mantido** — nesse caso ele é
  load-bearing (ver `dfm-fmx-sem-bom.md`) e a correção certa, renomear para ASCII, é das skills.

### 6.2 `hook-inject`

1. Node < 22.13 → sai com código 0, sem saída.
2. Lê o payload; `prompt` vazio → sai.
3. **Sinal explícito** (`delphi-intent.ts`), qualquer um de:
   - extensão `.pas .dfm .dpr .dpk .dproj .fmx .inc`;
   - código de compilador `\b[EFWH]\d{4}\b`;
   - termo do ecossistema (lista em `delphi-intent.ts`, sem diferenciar maiúsculas): Delphi, Object
     Pascal, RAD Studio, FireMonkey, FMX, VCL, FireDAC, DataSnap, Horse, Boss, DUnitX, Spring4D,
     TForm, TDataModule, TFDQuery, TFDConnection, LiveBindings, Indy, ACBr, Skia4Delphi.
4. Sem sinal explícito: só segue se `cwd` contiver `*.dpr`/`*.dproj` **e** o melhor resultado tiver
   score ≥ `STRONG_SCORE`.
5. Busca (`search.ts`) com limite 3; cada trecho via `snippet(sections, 2, '', '', '…', 48)`, máx.
   400 caracteres.
6. Saída JSON:
   `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"…"}}` com cabeçalho
   `[DELPHI-DEV KNOWLEDGE]`, a diretriz "canonical prevalece sobre community; peça o arquivo inteiro
   com kb_get" e um trecho por linha rotulado `[tier/category] path`.
7. Prazo de 1 s (timer); estourou → sai 0 sem saída. Qualquer exceção → log, sai 0.

### 6.3 Validação obrigatória: comando sem Node

Se `node` não existir, a linha de comando falha **antes** do nosso código. Forma candidata:
`command -v node >/dev/null 2>&1 && node "…"; exit 0`. Validar no Windows se a falha aparece para o
usuário e trocar a forma se preciso: **Claude Code neste sprint**; Codex (com `commandWindows`) e
OpenCode nos Sprints 3 e 4, quando seus manifests existirem. Resultado registrado nesta seção.

## 7. MCP `delphi-dev-kb` (`plugin.json` → `mcpServers`)

```json
"mcpServers": {
  "delphi-dev-kb": {
    "command": "node",
    "args": ["${CLAUDE_PLUGIN_ROOT}/runtime/kb-mcp.mjs"]
  }
}
```

Não usar `.mcp.json` na raiz: o Claude Code também o carrega como MCP do projeto para quem trabalha neste repositório, e lá `${CLAUDE_PLUGIN_ROOT}` não existe.

| Ferramenta | Entrada | Saída |
|---|---|---|
| `kb_search` | `query`, `limit` (1–5, padrão 3), `tier?` | trechos rotulados, com `path` |
| `kb_get` | `path` (relativo a `knowledge/`) | arquivo inteiro; recusa caminho fora da base |
| `kb_update` | `force?` | resumo: novos, alterados, removidos, por tier, `pluginVersion` remoto |
| `kb_health` | — | fonte ativa, commit, contagem por tier, última checagem e resultado, versão do Node, versão do plugin |
| `kb_prefs` | `get` ou `set {suggestions, offline}` | preferências atuais |

Node < 22.13: o servidor sobe e responde `kb_search` com erro estruturado explicando a
degradação; `kb_get`, `kb_update`, `kb_health` e `kb_prefs` funcionam (não usam SQLite).

## 8. Comandos

### 8.1 `/update` (novo)

1. Chama `kb_update(force: true)` e mostra o resumo. Sem MCP: explica o modo reduzido (§9).
2. Compara `pluginVersion` remoto com o instalado. Se houver versão nova, mostra o comando do agente
   em uso e oferece rodar com confirmação; avisa que é preciso **reiniciar a sessão**:
   - Claude Code: `/plugin` → marketplace `delphi-dev` → atualizar (ou `claude plugin update`).
   - Codex: atualização pelo marketplace (subcomando exato confirmado no Sprint 3).
   - OpenCode: `npx delphi-dev update`.
3. Bilíngue.

### 8.2 `/about` (ampliado)

Mantém o que tem e acrescenta um bloco **Status**, alimentado por `kb_health`: versão do plugin,
agente em uso, Node, base (fonte, commit curto, arquivos por tier, última atualização). Sem MCP:
"Base em modo reduzido". Tabela de comandos ganha `/update` e a descrição nova do `/contribute-kb`.

### 8.3 `/contribute-kb` (reescrito) e skill `delphi-contribute` (nova)

**Gatilho de sugestão** — regra curta na `delphi-standards`: depois de resolver algo não trivial (erro
de compilação que exigiu investigação, armadilha de framework, comportamento de IDE não óbvio),
**no máximo uma vez por sessão**, e nunca se `kb_prefs.suggestions == "off"` (sem MCP: ler
`~/.delphi-dev/config.json`), oferecer a contribuição seguindo a skill.

**Protocolo da skill**:

1. **Redigir** um aprendizado: frontmatter (`title`, `category` ∈ bugs/architecture/patterns/failures/
   general, `tags` em pt e en, `source: community`, `lang`) + corpo **Sintoma → Causa → Solução →
   Exemplo genérico**, no idioma da conversa, com identificadores didáticos (`TCliente`, `FNome`),
   nunca nomes do projeto do usuário.
2. **Escanear** com `kb-cli scan` (ou `secret-scan` embutido na skill como lista de verificação quando
   não houver Node). Achado → bloquear, apontar, reescrever, escanear de novo.
3. **Mostrar** o texto exato com o aviso:
   - pt-BR: "Vou compartilhar só o texto abaixo — um aprendizado sobre desenvolvimento Delphi.
     Nenhum código, dado, arquivo ou credencial do seu projeto vai junto. Revise antes de aprovar."
   - en-US: "I'll share only the text below — a learning about Delphi development. No code, data,
     files or credentials from your project go with it. Review it before approving."
4. **Perguntar** com a ferramenta de pergunta nativa do agente (fallback: opções numeradas):
   Aprovar / Recusar / Não mostrar novamente (sugestão) ou Aprovar / Recusar (manual).
   "Não mostrar novamente" → `kb_prefs set suggestions=off`.
5. **Enviar** com `kb-cli contribute <arquivo>` (§8.4) e mostrar o link.

### 8.4 Envio (`contribute.ts`)

- **Com `gh` autenticado** (`gh auth status` = 0):
  `gh repo fork adrianosantostreina/delphi-dev --clone=false` (idempotente) → `gh repo sync` do fork →
  branch `kb/<data>-<slug>` via `gh api …/git/refs` → arquivo
  `knowledge/community/<data>-<slug>.md` via `gh api -X PUT …/contents/…` → `gh pr create --repo
  adrianosantostreina/delphi-dev --head <user>:<branch>`.
- **Sem `gh`**: URL
  `https://github.com/adrianosantostreina/delphi-dev/issues/new?template=kb-contribution.yml&title=…&learning=…`.
  Se a URL passar de 7.500 caracteres: abre a URL sem `learning`, copia o texto para a área de
  transferência (`clip`, `pbcopy`, `wl-copy`/`xclip`) e avisa.
- Abrir navegador: `start ""` (Windows), `open` (macOS), `xdg-open` (Linux).

### 8.5 `/sync-kb` (só do mantenedor)

Vive em `.claude/commands/sync-kb.md` e `.agents/skills/sync-kb/SKILL.md` **deste repositório** —
comando de projeto, não distribuído no plugin. Usa `kb-cli sync`.

1. Origem: `~/.claude/shared/delphi-knowledge/*.md`, exceto `INDEX.md`, `AGENTS*.md`, `CLAUDE.md`.
2. Destino: `fmx/` se o nome começa com `fmx-` ou a primeira linha H1 contém "FMX"/"FireMonkey";
   senão `core/`. Arquivo que já existe em `core/` ou `fmx/` mantém a pasta onde está.
3. Estado em `knowledge/.sync-state.json`: `{ "<nome>": { "dest": "core", "sha256": "<hash da última sincronização>" } }`.
4. Classificação: **novo** (não existe no destino), **igual**, **alterado** (destino == estado; origem
   mudou), **conflito** (destino ≠ estado — editado no plugin depois do último sync; nunca
   sobrescrito, mostra diff), **só no plugin** (informativo).
5. Cópia **byte a byte** (sem transformar). Atualiza o `INDEX.md` da pasta com uma linha por arquivo
   novo (`- [nome.md](nome.md) — <H1>`).
6. **Dry-run por padrão** (`--apply` grava). Commit com confirmação; push com confirmação.

| Recurso | ≥ 22.13 | 18 – 22.12 | sem Node |
|---|---|---|---|
| Skills, commands, agentes | ✅ | ✅ | ✅ |
| `fix-encoding` | ✅ | ✅ | ❌ silencioso (§6.3) |
| Atualização diária / `/update` | ✅ | ✅ | ❌ |
| `kb_search` | ✅ | ⚠️ erro explicativo; skills procuram nos `.md` | ⚠️ skills procuram nos `.md` embutidos |
| `kb_get` | ✅ | ✅ | ❌ (MCP não sobe) |
| Injeção automática | ✅ | ❌ silencioso | ❌ silencioso |
| Sugestão / envio de contribuição | ✅ | ✅ | ⚠️ scanner só na CI |

As skills (`delphi-standards`, `delphi-write`, `delphi-laudo`) ganham a instrução: *"se `kb_search`
não estiver disponível, procure em `~/.delphi-dev/kb-cache/current/` e, se não existir, em
`knowledge/` na raiz do plugin."*

## 10. CI

### 10.1 `build-kb.yml` (substitui `build-rag.yml`)

- Gatilhos: push em `master` tocando `knowledge/**` ou `.claude-plugin/plugin.json`; `workflow_dispatch`.
- Node 22. `node runtime/kb-cli.mjs validate knowledge/` (frontmatter de community, tamanhos,
  `secret-scan` em community) → `node runtime/kb-cli.mjs manifest knowledge/ --out kb-manifest.json`.
- Publica o asset no release **`kb-latest`** com `prerelease: true` e `make_latest: false` — **nunca**
  pode virar o *Latest*, senão quebra o download do `rag.db` dos installers v3.x.

### 10.2 `validate-community.yml` (ampliado)

Mantém o allowlist de caminhos e a passagem por variável de ambiente. Troca o validador pelo
`kb-cli validate` (bloqueia em frontmatter, tamanho e **segredo**) e acrescenta `kb-cli similar`, que
escreve no **resumo do job** os 3 arquivos mais parecidos (FTS5 sobre título + tags) — aviso, não
bloqueio. Não é comentário no PR porque PR de fork recebe token só de leitura.

### 10.3 `kb-issue-to-pr.yml` (novo)

- Gatilho `issues: [labeled]`, só quando o rótulo é `kb-aprovado`.
- Confere `gh api repos/…/collaborators/$SENDER/permission` ∈ {admin, maintain, write}; senão encerra.
- Corpo da issue entra **só por variável de ambiente** em `kb-cli issue-to-file` (extrai a seção do
  campo `learning` do formulário). Nunca interpolado em `run:`.
- **Roda a mesma validação do §10.2 dentro do job**, porque PR aberto com `GITHUB_TOKEN` não dispara
  outros workflows.
- Cria `kb/issue-<n>`, commita, `gh pr create` com "Closes #<n>".

### 10.4 `runtime-check.yml` (novo)

Em todo PR e push que toque `kb/`, `runtime/` ou `knowledge/`: `npm ci` em `kb/`, typecheck,
`npm run build:runtime`, `git diff --exit-code runtime/`, `npm test`. O `kb/` é **pacote isolado**
(fora dos workspaces npm) com `package-lock.json` **commitado**, para o bundle ser reproduzível.

### 10.5 Formulário `.github/ISSUE_TEMPLATE/kb-contribution.yml`

Campo `textarea` com `id: learning` (obrigatório) e caixa de confirmação "o texto não contém código,
dados ou credenciais do meu projeto".

## 11. Erros

- Hooks saem **sempre** com 0; erros vão para `~/.delphi-dev/logs/kb.log`.
- MCP devolve erro estruturado por ferramenta; o processo não cai.
- Atualização é atômica; falha preserva o snapshot anterior.
- `secret-scan` é *fail-closed*.
- `kb_get` rejeita caminho com `..`, absoluto ou fora de `knowledge/`.

## 12. `secret-scan`

Achado = `{ line, kind, excerpt }`. Padrões:

| kind | Padrão (resumo) | Exceções |
|---|---|---|
| `private-key` | `-----BEGIN [A-Z ]*PRIVATE KEY-----` | — |
| `aws-key` | `AKIA[0-9A-Z]{16}` | — |
| `github-token` | `gh[pousr]_[A-Za-z0-9]{36,}` | — |
| `npm-token` | `npm_[A-Za-z0-9]{36}` | — |
| `jwt` | `eyJ[\w-]{10,}\.[\w-]{10,}\.[\w-]{10,}` | — |
